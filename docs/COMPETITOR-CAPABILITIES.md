# Threads MCP capability comparison

Checked: **2026-10-23, Asia/Taipei**. Scope: five public projects and current Meta documentation. GitHub connector reads confirmed source registrations and README/registry text; no competitor was installed, authenticated or exercised. A registered tool is implementation evidence, **not** proof that it currently succeeds against Threads. This bounded review cannot establish a worldwide "most complete" ranking.

## Baseline at start of this comparison

`src/server.ts` registers **13 tools**: `threads_status`, `threads_search`, `threads_get_post`, `threads_get_replies`, `threads_get_profile`, `threads_get_feed`, `threads_get_connections`, `threads_check_relationship`, `threads_read_page`, `threads_browser_snapshot`, `threads_browser_scroll`, `threads_prepare_action`, `threads_execute_action`.

Dedicated structured reading covers observed posts/counts, conversations, profiles, follower/following windows and positive/unknown relationship checks. Search combines web keyword discovery with local multilingual embedding and fuzzy lexical ranking. It is **not** semantic search over the entire Threads corpus. The generic snapshot/prepare/execute interface is not equivalent to dedicated, verified publish/like/follow/edit/delete workflows.

Local verification is recorded in [VERIFICATION.md](VERIFICATION.md): one all-hidden runtime 0.1.2 cycle observed 20 classified replies, 20 followers, 20 following entries, 21 search posts and six profile posts, with connection retained. This does not establish complete lists or reliability for every account/page. Own liked/saved feeds, profile replies/media/reposts sections, messages, notifications and public writes are code surfaces or UI fallback, not all live-accepted workflows. Media file upload remains manual.

## Practical gaps against this sample

| Area | Our current state | Concrete next capability / acceptance condition |
|---|---|---|
| Search and discovery | Local semantic/fuzzy reranking, keyword variants, author/date/min-like filters over observed corpus | Add dedicated user search, explicit top/recent mode, topic-tag/media filters and resumable discovery. Evaluate semantic ranking and recall separately; do not imply complete platform coverage. |
| Own content, likes, replies, mentions | Profile sections and liked/saved routes exist; specific flows not all validated. Notifications currently visible text, not a normalized mentions feed. | Verify own replies/liked/saved end-to-end. Add normalized notification/mention types and filters, with provenance and partial coverage. Keep "likes count", "who liked", "my liked posts" and "like action" distinct. |
| Conversation and relationships | Root-aware reply classification, partial followers/following, positive-or-unknown relationship | Add bounded nested reply expansion, incremental deduplication, continuation checkpoints and independent count/coverage diagnostics. A displayed total is not proof all comments were collected; an absent person in a sample is not a negative relationship. |
| Write workflows | Fresh snapshot + prepared one-shot interaction; writes disabled by default; results unverified until inspected | Dedicated create/reply/quote/like/unlike/repost/follow/delete workflows with before/after state and outcome verification. Bintang has named tools here; a generic click tool is not parity. Existing authorization requirements remain in force. |
| Media and multi-post composition | Reads media references; file picker/upload manual | Explicit image/video/carousel upload pipeline, limits and processing status, alt text and multi-post chains. Must validate staged media and actual publication separately. |
| Analytics | Current observed engagement values and local search index | Optional official API adapter for authorized own-post/account insights; time-series snapshots, growth and reporting. Sampled public counts cannot substitute for private insights or historical growth. |
| Moderation | Generic web UI fallback only | Dedicated hide/unhide, reply audience, pending approvals, moderation state verification. Meta and mikusnuz expose concrete surfaces. |
| Scheduling, export, operations | Persistent bridge host and local index; no product publish scheduler or export MCP tools | Explicit durable scheduling with timezone, cancellation and outcome states; JSON/CSV export and batch reads. Competitors expose these today in source. Keep notification delivery separate from retry/work scheduling. |

Priority inference: finish reliable read coverage and dedicated user/mention/liked/saved tools first; then verified write/media workflows; then analytics/moderation through an optional official adapter; finally durable scheduling/export/monitoring. This would combine strengths of browser access and official endpoints, but each feature needs its own evidence. A credible product claim is "broad Threads research and account-operation toolkit with verified capability coverage", not "everything a human can do" or "world's most complete".

## Official API boundaries checked today

- [Keyword search](https://developers.facebook.com/documentation/threads/keyword-search) (page updated 2026-01-21): `threads_keyword_search` plus `threads_basic`; before permission approval, search is limited to the authorized user's own posts. Approved public search supports top/recent, keyword/tag, media type, time range and exact author. Limit: 2,200 queries per user per rolling 24 hours, across apps; up to 100 results/request.
- [Profiles](https://developers.facebook.com/documentation/threads/threads-profiles) (updated 2026-04-13): `threads_profile_discovery` for public exact-username lookup. Standard Access only exposes selected Meta official accounts; eligible public profiles have at least 100 followers; 1,000 lookups per rolling 24 hours. Public-profile aggregate likes are not arbitrary post-level insights or liker lists.
- [Insights](https://developers.facebook.com/documentation/threads/insights) (updated 2026-01-30): describes the user's **own** Threads insights and requires `threads_manage_insights`; media metrics include views, likes, replies, reposts, quotes and shares. Do not turn a competitor's broad "analytics" label into a claim of unrestricted third-party data.
- [Reply management](https://developers.facebook.com/documentation/threads/reply-management) (updated 2026-02-13): own-post reply moderation includes hide/unhide, reply controls and pending approvals. Hiding a top-level reply affects its nested replies; nested replies are not independently hideable through that endpoint.

All four official pages were fetched successfully (HTTP 200) during this comparison. No authorized API request was made.

## Local implementation update during the same task

Server v0.2.0 now registers 17 tools, adding `threads_research`, `threads_my_activity`, `threads_find_mentions`, and `threads_get_notifications`. It adds persistent account-scoped collections, source provenance, date upper bounds, exclusions, reply-type filtering, author diversity and optional bounded thread expansion. Exact-handle mention candidates are distinguished from name/brand matches. The original 13-tool baseline above remains a dated comparison snapshot; see VERIFICATION.md for final live acceptance. Dedicated write/media/scheduling/API insights/moderation gaps remain.

## v0.3.0 implementation follow-up — 2026-10-24 Asia/Taipei

The server now registers 42 tools. Bintang's named browser actions and local scheduling informed workflow coverage; Mikusnuz's official API surface and current Meta documentation informed the optional typed adapter. Implementation is independently authored. Added named browser preparation/execution, bounded local-file staging, durable drafts/schedules/chains, explicit API mutations, API media/carousel/alt text/moderation, browser own-account Insights, row-local notification candidates, reply inbox, incremental dedupe, sampled trends and batch/export with provenance.

The scheduled publisher uses the official API, with account identity, immutable authorization, container status and post read-back checks. It does not claim to replicate every competitor's browser-based unattended publishing. Browser replies/quotes/media can remain uncertain when the intended relationship or remote attachment cannot be verified. Notification rows without a reliable action label retain unknown type. Published-post editing, complete follower graphs, liker identity coverage and full platform-wide discovery remain outside verified structured coverage. Source coverage and tool count are not a worldwide completeness ranking; see the verification record for actual account tests.
