# Browser workflow publisher

`publishBrowserDraft(service, social, draft, context, options?)` adapts explicitly authorized immutable workflow parts to the existing selected-browser `SocialActions` controller. It never connects to the official API, obtains credentials, or retries a social commit. Browser identity must match the draft and workflow account username. Plain numeric account IDs are rejected; a genuinely numeric username must be written with an explicit `@` prefix.

The caller must invoke this adapter **outside** `service.serial`. The adapter first calls public `browserRead()` to establish the selected account, then acquires one service mutex covering account recheck, snapshot, navigation, staging and execution. Driver-level reads inside that mutex avoid nested acquisition of the non-reentrant service queue. Use the same `SocialActions` instance and write reservation as other browser writers. Do not independently wrap the adapter in another service queue.

Supported draft forms are nonempty text (up to 500 Unicode characters), a text reply with an explicit author-qualified Threads `replyUrl`, and a text quote with `quoteUrl`. A later chain part requires `context.previousPostUrl` from the prior **confirmed** outcome; a numeric ID or shortcode is insufficient for root reply navigation. The returned `postId` is the observed permalink shortcode, not an official API numeric media ID. The caller should retain `postUrl` for chain continuation.

All scheduled media and alt text are rejected before browser reads/navigation/uploads. This adapter does not silently drop attachments, download media URLs, or infer final media content from upload progress. Numeric `quotePostId` is rejected: browser drafts must supply the URL alone. Standalone media staging remains a separate workflow and does not grant authorization to schedule a partially verified upload.

Before navigation, a visible dialog, nonempty composer, attachment or ambiguous editor blocks execution so existing draft state is preserved. Read-only `composerState` metadata permits a known empty inline composer; global searchboxes are not treated as drafts. With older runtimes lacking this metadata, non-search editable controls remain conservatively blocked. After staging, the exact account, action, target and text are compared with the immutable draft. The adapter consumes the preparation through one `social.execute` call. Only a verified non-noop publication with a new author-qualified own-account `postUrl` is returned as `confirmed`. The result retains that URL, shortcode and bounded evidence.

Precommit failures return `status: failed`. A commit/verification uncertainty throws `BrowserPublishingError` with `outcome: unknown`, `retryable: false` and bounded `evidence`. `WorkflowStore.runDue` conservatively records thrown publisher failures as uncertain and never replays the part. Integrations may preserve the error's safe evidence in that record. An explicit stop before commit preserves any staged draft; it does not dismiss or erase it.

Reply/quote confirmation depends on `SocialActions` proving the intended relationship. A runtime that only sees a new post and reports `new-post-observed-relation-unverified` results in uncertainty; the adapter does not promote that observation into success or continue the chain. A successful fixture proves adapter behavior only. No real browser publication, reply or quote was performed when this adapter was implemented.

Offline tests cover queue ownership, account mismatch/switch, early media/ID rejection, explicit target routing, chain URL requirements, draft preservation, changed prepared content, Stop, cooldown rejection, and one-shot uncertain outcomes. Root integrations must pass a prior confirmed `postUrl` in the workflow context and must keep scheduled browser execution behind explicit account/content authorization and the enabled write setting.

The v0.4.0 integration waits for the shared write cooldown before staging. The cancellable wait occurs inside the service mutex, before a fresh account/draft read and any navigation; waiting does not reserve another write. Cancellation is checked during bounded 250ms waits. This avoids failing a fast second chain part merely because the first part was confirmed quickly.
