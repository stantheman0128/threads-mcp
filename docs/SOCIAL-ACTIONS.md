# Prepared browser social actions

`SocialActions` coordinates a staged browser action with a one-use runtime token. The service must run its `prepare` and `execute` calls under the same operation mutex as other navigation and browser tools. Both staging and commit require `THREADS_ALLOW_WRITES=true`. Tests never mutate a real Threads account.

Browser Stop/disconnect cancels the current social preparation and advances a generation guard. Pending menu/composer waits cannot continue to fill text, click another preparation control, or create a usable token after cancellation. Already entered draft text remains available for manual review.

`SocialActions.inspect` is read-only and remains available with writes disabled. It never opens a menu/composer or fills text. A missing menu returns `menu-required`; compose inspection does not require draft text. Verification after a successful single dispatch retries only bounded UI-readiness errors; account/target failures stop immediately. A same-document route change to a new own-post permalink may be verified using the retained commit evidence. A full document navigation that loses that evidence remains uncertain.

Navigate to the exact canonical post/profile URL first (home for publication). Prepare binds the account, target, unique DOM scope, control fingerprint and exact text. It may open an explicit menu or empty composer and stage text, but does not click submit. Execute revalidates those bindings, consumes its token before input, dispatches once, then performs bounded read-only verification. Transport failure, changed account, missing result or unchanged state returns `outcome-uncertain`; it never retries the commit. Application success requires observable intended state, not a successful click or closed composer.

Supported action names are like/unlike, save/unsave, repost/unrepost, follow/unfollow, publish/reply/quote and delete. Availability depends on independently recognizable current UI:

- Like/unlike uses one isolated post card matching the exact permalink. Save and repost use an explicit `aria-haspopup` menu trigger in that card and one exact menu action; ambiguous or undocumented triggers stop preparation.
- Follow/unfollow identifies the exact profile using its heading, visible username and matching profile tabs, or an explicit semantic profile header. A sticky column heading that reaches an ancestor of the same profile does not widen the scope: only the smallest independently matched scope is retained, while separate duplicate profiles remain ambiguous. Controls after the tabs, in post timelines or suggested-profile sidebars are excluded. Following is prepared without clicking; authorized execution dispatches it once and checks for the resulting Follow state. If it opens a confirmation instead, the result is `confirmation-required`, with no automatic confirmation click. Pending follow requests are not reported as confirmed following.
- Text publication stages at most 500 Unicode characters in one empty, uniquely identified composer. Existing drafts, dialogs or attachments are preserved. Quote composers must visibly link the exact source post. A reply composer may instead carry the observed reply header and a preview matching the exact source author, timestamp and complete visible body; that same preview and source-card identity are checked again before commit. Original-post media outside the editor's composer body is excluded from new-attachment checks.
- Publication verification requires a new permalink absent before submission, the current account author, exact visible submitted text and a visible creation timestamp within the commit window. For replies and quotes, a new post alone does not prove its relationship to the target; that result remains unverified. Media publication also stays unverified when the visible remote attachments cannot be matched to the uploaded bytes. These are explicit current browser limitations.
- Delete requires both an exact current-account permalink and a matching visible author link in that card. Preparation opens only its More menu and binds the exact Delete menu item. Authorized execution dispatches that item once. A new confirmation dialog returns `confirmation-required` without clicking its final button. Disappearance alone returns `deletion-unverified`; it never claims server deletion.

Menu preparation waits briefly for the exact action state after opening the menu, because React can replace the initial overlay shell before its action rows appear. The original post card and menu trigger must remain connected and associated; it never clicks again or binds another card. It selects the final unique populated menu, also checks `aria-controls` when present, and checks account, target and cancellation during that bounded wait. Controlled `AMBIGUOUS_UI_*` codes identify account navigation, post scope, profile scope, menu trigger/content or action state/control without including private page content in error results. `TARGET_CHANGED_MENU_CARD` and `TARGET_CHANGED_MENU_TRIGGER` distinguish removal of those original identity bindings from a route change.

Current fixture coverage validates locking, disabled writes, cooldown, token consumption, lost transport results, DOM ambiguity, exact post identity, untouched existing drafts, manual takeover and publication evidence. These offline fixtures do not assert that every live Threads locale/layout is supported. Unsupported live layouts fail closed with actionable error codes.

For local media, first open an empty composer and use the bounded media-upload tool. Its result supplies `mediaToken`; pass that token with the exact text to social preparation. The runtime validates the approved same-composer File objects and visible previews before staging text and again before commit. It refuses attachments added to an unapproved text-only draft. Uploading or staging a preview alone never counts as publication.

Its deterministic preparation, exact account/target validation and post-dispatch verification are local design choices.

v0.3.1 includes regression coverage for the observed Traditional Chinese labels `收回讚193`, `轉發3` and `已回覆`, plus own-post Insights links. Only canonical `/@username/post/code` links define post identity; `/insights/post/code` is not a separate target post. The actual account inspection failed closed before this fix. Live read-only acceptance awaits loading v0.3.1; no public social write has been used for verification.

v0.3.2 additionally reads a unique directly owned SVG's accessible action name from `aria-label`, `title`, or a direct `<title>` child. Multiple or conflicting icon names remain ambiguous. Actual account read-only inspection passed with exact account/target and already-liked state; no click was dispatched. Read results distinguish `extensionVersion` from `runtimeVersion`; stateful commands reject mismatched versions until the extension is reloaded and reconnected.
